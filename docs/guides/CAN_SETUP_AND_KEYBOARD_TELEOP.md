## 2. PEAK CAN 드라이버

### 문제

JetPack 6.2.2 커널에는 `CONFIG_CAN_PEAK_USB`가 빠져 있습니다. PCAN-USB(`0c72:000c`)를
꽂아도 `lsusb`에는 보이지만 네트워크 장치가 생성되지 않습니다.

```
$ modinfo peak_usb
modinfo: ERROR: Module peak_usb not found.
```

**`can2`가 없다고 배선부터 의심하지 마십시오.** 먼저 확인할 것:

```bash
lsmod | grep pcan
cat /proc/pcan
```

### 해결 — 공식 드라이버 소스 빌드

PEAK 공식 드라이버 `peak-linux-driver-8.20.0`을 netdev 모드로 빌드했습니다.
커널 헤더는 `nvidia-l4t-kernel-headers`로 이미 설치되어 있습니다.

| 위치 | 내용 |
|---|---|
| `~/peak-driver/peak-linux-driver-8.20.0/` | 드라이버 소스 |
| `~/peak-driver/install_pcan.sh` | 빌드·설치·검증 |
| `~/peak-driver/setup_can2.sh` | udev 고정 + can2 기동 |
| `~/peak-driver/check_drive_motors.sh` | 무동작 통신 확인 |

빌드 확인 포인트: 모듈 version이 **`Release_..._n`** 으로 끝나야 netdev 모드입니다.

```bash
$ modinfo ~/peak-driver/peak-linux-driver-8.20.0/driver/pcan.ko | grep -E "version|vermagic"
version:    Release_20250213_n          # _n = netdev
vermagic:   5.15.185-tegra SMP preempt mod_unload modversions aarch64
```

> **DKMS 미설치.** 커널이 바뀌면 `~/peak-driver/install_pcan.sh`를 다시 실행해야 합니다.
> 현재 JetPack 6.2.2가 pin 고정되어 있어 당분간은 안전합니다.

### 인터페이스 이름 고정

`can0`, `can1`은 Tegra 내장 `mttcan`이 점유합니다. PCAN은 udev로 `can2`에 고정합니다.

```
# /etc/udev/rules.d/45-pcan-can2.rules
SUBSYSTEM=="net", ACTION=="add", ATTRS{idVendor}=="0c72", ATTRS{idProduct}=="000c", NAME="can2"
```

```bash
sudo ip link set can2 type can bitrate 1000000 restart-ms 100
sudo ip link set can2 up
```

`can3`(리모콘, 250 kbps)은 **현재 미연결**입니다. 키보드 텔레옵은 이를 대체하기 위한 것입니다.

## 3. 모터 CAN ID

### 문제 — 전부 공장 기본값 0x141

첫 통전 시 4대가 모두 `0x141`로 응답했습니다. 질의 1회에 응답 4개가 오고, 교신마다
bus-error가 누적됩니다(질의 1회당 +20).

```
141  [8] 9A 00 ...              ← 질의 1회
241  [8] 9A 1A 1B 00 96 01 ...  ← 26°C, 40.6V
241  [8] 9A 19 1A 00 99 01 ...  ← 25°C, 40.9V
241  [8] 9A 19 1B 00 98 01 ...  ← 25°C, 40.8V
241  [8] 9A 19 1A 00 9A 01 ...  ← 25°C, 41.0V
```

### 3차년도 ID 배치

2차년도 대비 **횡이동이 2축으로 늘면서 상부체가 한 칸씩 밀렸습니다.**

| 통신 ID | CAN ID | 축 | 2차년도 | 상태 |
|---|---|---|---|---|
| 1 | `0x141` | **우측 구동륜** | 좌측 구동륜 | 완료·검증 |
| 2 | `0x142` | **좌측 구동륜** | 우측 구동륜 | 완료·검증 |
| 3 | `0x143` | 횡이동 #1 | 횡이동 | 완료·검증 |
| 4 | `0x144` | **횡이동 #2** (신규) | X축 | 완료·검증 |
| 5 | `0x145` | X축 | Y축 | 미설정 |
| 6 | `0x146` | Y축 | Z축 | 미설정 |
| 7 | `0x147` | Z축 (리프팅) | Yaw | 미설정 |
| 8 | `0x148` | Yaw 회전 | — | 미설정 |

### ID 변경 절차

**반드시 버스에 1대만 남긴 채** 진행합니다. 같은 ID의 모터가 여러 대 있으면 변경
명령을 전부가 수신해 모두 같은 새 ID로 바뀝니다.

```bash
cd /home/koceti/ros2_ws/src/rebar_control/tools/motor

python3 change_motor_id_safe.py --probe                # 응답자 수 확인
python3 change_motor_id_safe.py --from 0x141 --to 3    # 통신 ID 3 으로
# → 모터 전원 OFF, 3초, ON
python3 change_motor_id_safe.py --probe                # 반영 확인
```

`change_motor_id_safe.py`는 **응답자가 정확히 1대일 때만** 쓰기를 수행합니다.
기존 `change_motor_id_0x20.py`에는 이 가드가 없으므로 사용하지 마십시오.

전원 재투입 전에는 **명령은 옛 ID로 받고 응답만 새 ID로** 하는 과도 상태입니다.
이 상태에서 다른 모터를 연결하면 명령이 겹칩니다.

> ### 경고 — `0x20`의 index를 순회 탐색하지 말 것
>
> index `0x05`가 Set CANID입니다. 페이로드 0으로 보내면 해당 모터 ID가 0(0x240 응답)이
> 됩니다. 실제로 "어떤 파라미터 명령이 지원되나" 훑다가 좌측 구동륜을 이렇게 날렸고,
> `20 05 00 00 01 00 00 00`으로 복구했습니다.
> 미지 명령 스윕은 읽기 전용이 확인된 코드에만 하십시오.

## 4. 펌웨어 특성 (RMD X4-36)

이 펌웨어에서 **동작하지 않는** 명령:

| 명령 | 기능 | 결과 |
|---|---|---|
| `0x90` | 단회전 엔코더 | 응답 없음 |

→ `joint_controller.py`의 홈 로직은 `0x90` 기반이라 **이 하드웨어에서 동작하지 않습니다.**

> **정정 (2026-09-08)**: 초기에 `0x30`/`0x31`(PID)이 미지원이라고 기록했으나 **틀렸습니다.**
> `0x30` 은 `DATA[1]` 에 **인덱스**가 필요한데 0 으로 보내서 빈 응답을 받았고, 여기에
> 이전 질의의 응답이 수신 버퍼에 남아 섞이면서 오판했습니다. **PID 는 CAN 으로
> 읽고 쓸 수 있습니다.** 아래 8장 참조.

**동작하는** 명령:

| 명령 | 기능 | 비고 |
|---|---|---|
| `0x60` | 멀티턴 엔코더 | `= 0x61 - 0x62` (검증됨) |
| `0x61` | 멀티턴 원본 | `mod 262144`가 단회전 절대 위치 |
| `0x62` | 멀티턴 영점 오프셋 | ROM 저장, 전원 무관 |
| `0x30`/`0x31`/`0x32` | PID 읽기 / RAM 쓰기 / ROM 쓰기 | `DATA[1]`=인덱스, `DATA[4:8]`=float32 LE |
| `0x42` / `0x43` | 가감속 읽기/쓰기 | **값은 모터축 기준 — 출력축 환산은 ÷36** |
| `0x92` / `0x94` | 멀티턴/단일턴 각도 | **전원 인가 시점 기준** |
| `0x9A` / `0x9C` | 상태 1 / 2 | 온도·전압·에러 / 전류·속도·각도 |
| `0xA2` / `0xA4` | 속도 / 절대위치 제어 | 모두 **출력축 기준** |

**엔코더 1회전 = 262144 counts (18bit).**

### 속도 명령은 출력축 기준

30 dps로 3.004초 구동 → 출력축 기대 회전 90.1°:

| 모터 | 실측 Δ | 실측/기대 |
|---|---|---|
| 0x141 | +90.15° | **1.000** |
| 0x142 | +89.75° | **0.996** |

→ 감속비가 12.6:1(X4-10) → 36:1(X4-36)로 바뀌어도 **cmd_vel 환산식은 그대로 유효**합니다.

## 5. 구동륜

### 좌/우 배정과 부호 (검증 완료)

- **통신 ID 1(`0x141`) = 우측**, **통신 ID 2(`0x142`) = 좌측**
- cmd_vel 전진(`linear.x > 0`)에서 **좌측 `0x142` = 양수(+), 우측 `0x141` = 음수(−)**
- 좌우 바퀴가 마주보게 장착되어 부호가 반대여야 같은 쪽으로 굴러갑니다

검증: `+0.1 m/s` 2초 → `0x142` CCW **+125.96°**, `0x141` CW **−126.31°** (좌우 편차 0.3%),
전진 방향 육안 확인.

구현 위치:

| 파일 | 내용 |
|---|---|
| `config/robot_control.yaml` → `position_control_node:` 섹션 | `left_motor_id: 0x142`, `right_motor_id: 0x141` |
| `position_control_node.py` `cmd_vel_callback` | `left = +int(left_dps*100)`, `right = -int(right_dps*100)` |

`rebar_base_control/can_sender.py`의 "오른쪽만 반전" 규약과 일치합니다.

## 6. 횡이동 2축

### 부호 규약 (검증 완료)

- **`0x143` = +1, `0x144` = −1**
- 두 모터가 마주보게 설치되어 **동일 부호를 주면 기구가 서로 반대로** 갑니다.
  반대 부호를 줘야 같은 방향으로 갑니다.
- **+방향 = 좌측 횡이동**

> **주의:** 두 축은 기계적으로 연결되어 있지 않아 **반대로 움직여도 전류가 튀지 않습니다.**
> 전류가 낮다는 이유로 "같은 방향"이라 판단했다가 육안 확인으로 뒤집었습니다.
> **방향은 반드시 눈으로 확인하십시오.**

### 동작

12시 정렬 → ±360° 회전. **1회전 = 리드스크류 1바퀴 = 50 mm (7.2 °/mm)**.

2회 연속 회전 반복 오차:

| 축 | 1회전 | 2회전 | 판정 |
|---|---|---|---|
| `0x143` | −0.25° | −0.25° | 일정 — 누적 안 됨 |
| `0x144` | +0.13° | +0.15° | 일정 — 누적 안 됨 |

### 홈(12시) 기준은 `0x61`

`0x92`/`0x94`는 전원 인가 시점 기준이므로 홈 기준으로 쓸 수 없습니다.
**`0x61 mod 262144`(단회전 절대)를 기준으로 씁니다.**

전원 재투입 검증 결과:

| 항목 | `0x143` | `0x144` | 판정 |
|---|---|---|---|
| `0x61 mod 262144` | 51072 → 50592 (−0.66°) | 39583 → 39426 (−0.22°) | **유지** |
| `0x62` 영점오프셋 | 123831 → 123831 | 197752 → 197752 | **완전 동일** |
| `0x60` 멀티턴 | 451529 → −73239 | −420312 → 103818 | **리셋** |
| `0x92` 각도 | 620.08° → −100.57° | −577.21° → 142.57° | **리셋** |

미세한 차이는 전원이 끊길 때 기구가 밀린 것(0.09 mm 수준)입니다.

**의미:**
- 12시 홈 복원은 가능합니다.
- **"몇 번째 50 mm 스텝인지"는 전원 후 복원 불가**입니다. 회전수가 리셋되므로
  **상대 이동(±50 mm)만 안전**합니다. 절대 위치가 필요하면 소프트웨어 카운터
  영속화나 리밋 센서가 필요합니다.

### 캘리브레이션

12시 위치는 `tools/motor/lateral_home.json`에 저장됩니다.

```bash
cd /home/koceti/ros2_ws/src/rebar_control/tools/motor

python3 lateral_dual.py status                                # 현재 상태
python3 lateral_dual.py jog --motor 0x144 --dps 20 --sec 1.0  # 미세 이동
python3 lateral_dual.py set-home --motor 0x144                # 현재를 12시로 기록
python3 lateral_dual.py align                                 # 양축 12시 정렬
python3 lateral_dual.py --speed 50 rotate --turns +1          # 좌측 50mm
```

기구가 바뀌면 **양축 모두 다시 잡아야 합니다.** 2차년도 값(33.50°)은 3차년도에
유효하지 않습니다.

## 7. ROS 2 통합 구조

```
                    ┌──────────────────────┐
   키보드 입력  ───► │  teleop_keyboard     │
                    └───┬──────────────┬───┘
                        │ /cmd_vel     │ /lateral/step (Int32)
                        ▼              ▼
        ┌───────────────────────┐  ┌──────────────────────┐
        │ position_control_node │  │    lateral_node      │
        │  0x141 우 / 0x142 좌   │  │  0x143 #1 / 0x144 #2 │
        │  부호 반전 규약         │  │  raw 부호 규약        │
        └───────────┬───────────┘  └──────────┬───────────┘
                    └───────────┬─────────────┘
                                ▼
                              can2
```

| 파일 | 역할 |
|---|---|
| `rmd_robot_control/lateral_axes.py` | 횡이동 코어 (ROS 무관). 부호·0x61 홈·전류 보호 |
| `rmd_robot_control/lateral_node.py` | `/lateral/step` 구독 → 12시 정렬 + ±N회전 |
| `rmd_robot_control/teleop_keyboard.py` | 키보드 입력 → cmd_vel / lateral |
| `launch/teleop.launch.py` | 주행 + 횡이동 노드 동시 기동 |

### 토픽

| 토픽 | 타입 | 방향 | 설명 |
|---|---|---|---|
| `/cmd_vel` | `geometry_msgs/Twist` | → 주행 | `linear.x`, `angular.z` |
| `/lateral/step` | `std_msgs/Int32` | → 횡이동 | `+N` 좌측 N회전, `−N` 우측 |
| `/lateral/complete` | `std_msgs/String` | ← 횡이동 | `COMPLETE` / `FAILED` |
| `/lateral/state` | `std_msgs/String` | ← 횡이동 | 12시까지 거리·온도·에러 (2초 주기) |

> **`/joint_1/position`, `/joint_2/position`으로 `0x143`/`0x144`를 명령하지 마십시오.**
> `position_control_node`는 각도 부호를 반전해서 CAN에 보내고(`angle_control = int(-target*100)`),
> 횡이동 노드는 raw 규약을 씁니다. 두 경로를 섞으면 부호가 어긋납니다.

## 8. 키보드 텔레오퍼레이션

리모콘 CAN(`can3`)이 미연결이라 그 자리를 대신하는 간이 조작 수단입니다.

### 실행

```bash
# 터미널 1 — 백엔드
cd /home/koceti/ros2_ws && source install/setup.bash
ros2 launch rmd_robot_control teleop.launch.py

# 터미널 2 — 조작 (이 창에 포커스가 있어야 키가 먹습니다)
source /home/koceti/ros2_ws/install/setup.bash
ros2 run rmd_robot_control teleop_keyboard
```

런치 인자:

```bash
ros2 launch rmd_robot_control teleop.launch.py lateral_speed_dps:=30
```

### 조작키

| 키 | 동작 |
|---|---|
| `w` / `s` | 전진 / 후진 |
| `a` / `d` | 좌 / 우 제자리선회 |
| `q` / `e` | 좌 / 우 횡이동 (1회전 = 50 mm) |
| `space` | 즉시 정지 |
| `z` / `x` | 선속도 − / + (0.05 m/s 단위, 최대 0.5) |
| `c` / `v` | 각속도 − / + (0.1 rad/s 단위, 최대 1.0) |
| `?` | 도움말 및 횡이동 상태 |
| `Ctrl+C` | 정지 후 종료 |

### 안전장치

| 장치 | 동작 |
|---|---|
| **데드맨** | 주행키 입력이 0.3초 끊기면 자동 정지 |
| **전류 상한** | 횡이동 중 2.5 A 초과 시 양축 즉시 정지 |
| **회전 상한** | 횡이동 명령당 최대 4회전(200 mm) |
| **중복 차단** | 횡이동 진행 중 신규 명령 무시 |
| **종료 정지** | `Ctrl+C` 시 `cmd_vel` 0 발행 후 종료 |

초기값은 **0.10 m/s / 0.30 rad/s**로 낮게 잡혀 있습니다. `z/x`, `c/v`로 올리십시오.

### 튜닝 순서 (권장)

1. **바퀴를 띄운 상태**에서 방향과 폭주 여부만 확인
2. 바닥에 내리고 **낮은 속도부터**. 충분한 공간과 전원 차단 수단 확보
3. 가감속(`0x43`) 조정 — 현재 5000 dps/s

> **가감속을 20000으로 올릴 필요는 없습니다.** 5000 dps/s면 500 dps 도달에 100 ms로
> 이미 충분히 빠릅니다. 20000은 25 ms로 사실상 계단 입력이라 덜컥거림과 슬립을
> 만듭니다. X4-10 → X4-36으로 토크가 2.9배 커져 **명령한 가속도를 실제로 내므로**,
> 예전에 무해했던 값이 지금은 충격이 됩니다.

## 8-A. 주행 튜닝 (2026-09-08)

### 바퀴 반지름 실측

바퀴를 정확히 1회전시키고 이동거리를 쟀다 (`tools/motor/drive_measure.py`).

```
183 mm / 1회전  →  wheel_radius = 183/(2π) = 29.12 mm = 0.02912 m
```

| 설정 | 1회전 예상 | 오차 |
|---|---|---|
| `rmd_robot_control` 0.1 m (이전) | 628 mm | **+243 %** |
| `rebar_base_control` 0.02865 m | 180 mm | −1.6 % |

**`rmd_robot_control` 의 0.1 m 는 3.4배 틀린 값이었다.** 이 때문에 "0.1 m/s" 명령이
실제로는 0.029 m/s 로 나가고 있었다. `position_control_node:` 섹션에 0.02912 로 반영.

정격 498 dps 기준 최대 선속도는 **0.25 m/s**. 기존 `max_linear_vel: 1.0` 은 573 dps 를
요구하는 도달 불가값이었다. 좌우 바퀴 속도가 정격을 넘으면 **같은 비율로 축소**하는
클램프(`wheel_max_dps: 498`)를 추가했다 — 한쪽만 포화되면 궤적이 휘기 때문이다.

### 가감속 — 파라미터는 모터축 기준 (÷36)

정지 명령 후 로봇이 관성처럼 흘러가는 문제를 추적한 결과다.

```
0x42 읽기값 5000 → 실측 감속 138 dps/s     5000/138 = 36.2
0x43 으로 500 쓰기 → 실측 15 dps/s          500/15  = 33.3
```

**비율이 감속비 36 과 일치한다.** 속도 명령(`0xA2`)은 출력축 기준인데 가감속
파라미터만 **모터축 기준**이다. 문서에 이 구분이 없어 놓치기 쉽다.

| 설정값 | 출력축 | 0→180dps | 180dps 정지거리 |
|---|---|---|---|
| 5000 (이전) | 139 dps/s | 1.30 s | 59 mm |
| **20000 (현재)** | **556 dps/s** | **0.32 s** | **15 mm** |
| 40000 | 1111 dps/s | 0.16 s | 7 mm |

20000 적용 후 실측 감속 **537~589 dps/s**, 미끄러짐 **105~118° → 27~30°**.
`0x43` 은 **RAM+ROM 동시 저장**이라 전원을 꺼도 남는다.

### `0xA2` DATA[1] 은 최대 토크

`DATA[1]` = maxTorque, **정격 전류의 백분율**(uint8, 1 LSB = 1%). 0 으로 두면 힘 제어가
활성화되지 않는다. 노드는 `0x64`(100%)를 보낸다. 직접 CAN 을 쓸 때 빠뜨리기 쉽다.

### PID 튜닝 — 가능하지만 이 진동에는 효과 없음

`0x30` 읽기 / `0x31` RAM 쓰기 / `0x32` ROM 쓰기. `DATA[1]`=인덱스, `DATA[4:8]`=float32 LE.

| idx | 파라미터 | 공장값 |
|---|---|---|
| 0x01 / 0x02 | 전류루프 KP / KI | 1.5 / 0.05 |
| **0x04 / 0x05** | **속도루프 KP / KI** | **0.01 / 0.0001** |
| 0x07 / 0x08 / 0x09 | 위치루프 KP / KI / KD | 0.05 / 0 / 0.5 |

튜닝 중에는 **RAM(`0x31`)만** 쓸 것 — 전원 재투입으로 공장값 복귀된다.

**속도루프 KP 를 0.5배·2배로 바꿔 3회씩 반복 측정했으나, 게인 간 차이가 재현성
잡음(같은 게인 재측정 시 ±45%)에 묻혔다.** 게인으로는 선회 진동을 잡을 수 없다.

### 선회 진동 — 기구 공진

| 근거 | 내용 |
|---|---|
| 주파수 | **25~28 Hz 고정**. 속도가 180 dps 든 106 dps 든 동일 |
| 배음 | 2배음이 기본파의 6%, 3배음 0 → 톱니파(스틱-슬립) 아님 |
| 좌우 | 두 모터가 **정확히 같은 주파수** |
| 게인 의존성 | 없음 (위 참조) |
| 속도 의존성 | **선회 속도 절반 → 진동 33~61% 감소** (3회 반복, 편차 ±0.005~0.044A) |

제어가 아니라 **타이어 횡방향 마찰이 섀시 공진을 가진**하는 것으로 보인다.
대응은 운용(선회 속도 제한)이며, 근본 해결은 기구 영역이다.

→ `max_angular_vel` **1.0 → 0.5 rad/s**, 텔레옵 기본 각속도 **0.3 → 0.15 rad/s**.
   부수 효과로 선회 미끄러짐이 **29° → 7°** 로 줄어 각도 정밀도가 4배 좋아졌다.

### 전류 여유 — 전후진과 선회가 다르다

| 동작 | 평균 | 최대 | 정격(6.1A) 대비 | 정격 초과 샘플 |
|---|---|---|---|---|
| **전후진** | 1.54 A | 5.51 A | **25 %** | 0.0 % |
| **선회** | **4.51 A** | **7.63 A** | **74 %** | 2.9 % |

**전후진은 여유가 12배**(하드 18A 기준)로 연속 주행에 문제없다.
**선회는 평균이 정격의 74%** 로 연속 운전 여유가 거의 없다. 선회 20여 회 반복 시험에서
모터가 25 → **46 °C** 까지 올랐다.

**선회는 속도를 낮춰도 전류가 줄지 않는다** (180→90 dps 에서 4.4~5.2 → 4.3~5.0 A).
부하가 속도가 아니라 타이어 횡마찰에 지배되기 때문이다. 속도 감소로 얻는 것은
진동과 정지 정밀도이지 열 여유가 아니다.

> **운용 권고**: 자율주행 동선에 **연속 제자리 선회를 넣지 말 것.** 선회 사이에
> 직진이나 정지를 두어 냉각 시간을 확보한다. 온도 40 °C 를 넘기 시작하면 쉬어간다.

### 주행 모터 보호 (신규)

`position_control_node` 의 기존 보호에는 결함이 세 개 있었다 — 자세한 내용은 9장.
횡이동과 동일한 계층으로 교체했다.

| 계층 | 임계 | 조치 |
|---|---|---|
| 즉시 차단 | 18 A 초과 | 두 모터 **0x80 SHUTDOWN** |

| 스톨 | 속도<3 dps & 전류>3 A 가 0.7 s | 속도 0 + 0x81 |
| 온도 | 60 °C | 속도 0 + 0x81 |

### 수정 완료

| 이슈 | 내용 | 조치 |

### 미해결 — 확인 필요

| 이슈 | 내용 |
|---|---|
| **`wheel_radius` 불일치** | `rmd_robot_control` 0.1 m vs `rebar_base_control` 0.02865 m (실측 캘리브레이션 주석 있음). **3.5배 차이.** 바닥에서 "1 m 명령 → 실제 이동거리" 측정으로 확정 필요 |
| **`0x144` 리드 미검증** | 1회전 = 50 mm는 `0x143` 기준값. 신규 축은 리드가 다를 수 있음. 360° 돌리고 자로 실측 필요 |
| **`joint_controller.py` 동작 불가** | 홈 로직이 `0x90` 기반인데 이 펌웨어가 미지원. `0x143` 하드코딩 27곳, `auto_lateral_*` 상태변수 57곳. 상부체 ID 재배치와 함께 정리 권장 |
| **`lateral_motion.py` 미배선** | 리팩터링용으로 추출만 되고 어디서도 사용되지 않음 |
| **문서 불일치** | `README.md`, `ROBOT_CONTROL_ARCHITECTURE.md` 등이 2차년도 ID 배치(`0x141`=좌측, `0x144`=X축) 기준 |

### 운영 시 주의

**`ros2 launch`를 `Ctrl+C` 외의 방법으로 끊으면 노드가 살아남습니다.**
잔류 노드가 같은 토픽을 구독해 **서로 다른 값을 CAN에 쏘면 검증 결과가 뒤집힙니다.**
실제로 이 때문에 구동륜 방향 검증이 한 번 잘못 나왔습니다.

```bash
pgrep -f position_control_node     # 테스트 전 확인
pgrep -f lateral_node
```
