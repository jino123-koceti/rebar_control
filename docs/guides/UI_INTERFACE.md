# 외부 UI 연동 규격 (3차년도)

노트북에서 UI 를 만들 때 쓰는 **장비 쪽 인터페이스**다. 2차년도 UI 체인
(`zenoh_client` → `/mission/command`)과는 **토픽이 다르다** — 그대로 쓰면 명령이
아무 데도 안 닿는다.

- 도메인: **`ROS_DOMAIN_ID=33`**  (설정 안 하면 아무것도 안 보인다)
- 2차년도 장비는 도메인 0 을 쓴다. 33 으로 분리해 둔 이유가 그것이다.

---

## 1. 명령 — UI → 로봇

| 토픽 | 타입 | 값 | 하는 일 |
|---|---|---|---|
| `/homing_cmd` | `std_msgs/String` | `"all"` | **전체 호밍** |
| `/homing_cmd` | `std_msgs/String` | `"stop"` | 호밍 중단 |
| `/mission/start` | `std_msgs/Empty` | — | 미션 시작 (경로 주행 + 결속) |
| `/mission/abort` | `std_msgs/Empty` | — | 미션 중단 |
| `/stage/stop` | `std_msgs/Empty` | — | 상부 축 즉시 정지 |

### 꼭 지킬 것

- **호밍은 `"all"` 뿐이다.** 축 이름(`"x"` 등)은 **거부된다.** 축마다 간섭 구간이
  달라서, 일부만 호밍한 상태로 움직이면 프레임끼리 부딪친다 — 실제로 `/homing_cmd x`
  하나로 상부 프레임을 쳤다.
- **정지 버튼은 세 개를 모두 보내라.** `/homing_cmd "stop"` + `/mission/abort` +
  `/stage/stop`. 어느 한 노드가 죽어 있어도 나머지가 멈춘다. 멈추는 쪽은 중복이 안전하다.
- ⚠ **UI 정지를 1차 수단으로 삼지 말 것.** 가장 빠르고 확실한 것은 **리모콘 비상정지**다.
  UI 는 와이파이→HTTP→ROS 를 거치므로 느리고, 통신이 끊기면 눌러도 안 간다.
- **호밍은 자동으로 돌지 않는다.** 사람이 눌러야 한다. 되살아난 즉시 자동으로 돌면
  아무도 시키지 않았는데 장비가 움직이고, `respawn` 과 겹치면 크래시 루프가
  재호밍 루프가 된다.

## 2. 상태 — 로봇 → UI

전부 `std_msgs/String` 에 **JSON** 이 들어 있다.

### `/homing_status`

```json
{"state": "seek", "axis": "x", "detail": "x_min 탐색",
 "queue": ["yaw", "y"], "refs": {"z": -61.7, "x": -25.0}}
```

| 필드 | 뜻 |
|---|---|
| `state` | `idle` / `arm` / `seek` / `back_off` / `fine` / `offset` / `ready` / **`done`** / **`failed`** |
| `axis` | 지금 호밍 중인 축 (`null` 이면 없음) |
| `detail` | 사람이 읽을 설명. **실패 사유가 여기 들어온다** |
| `refs` | 축별 원점. **4개(`x`,`y`,`z`,`yaw`)가 다 차야 호밍 완료**다 |

### `/mission/status`

```json
{"phase": "run", "total": 5, "current": 1,
 "steps": [{"step": "tie", "state": "완료"}, {"step": "drive -500", "state": "진행"}],
 "detail": "..."}
```

| 필드 | 뜻 |
|---|---|
| `phase` | `idle` / `run` / **`done`** / **`failed`** |
| `total` / `current` | 전체 단계 수 / 지금 단계 번호(0-based, 없으면 `null`) |
| `steps[]` | `{step, state}` — `step` 은 `"tie"`·`"drive -500"` 같은 문자열 |
| `detail` | 실패 사유 |

### `/stage/status` (상부 축)

```json
{"pose": 1, "pose_detail": "1번 자세 (건 -16.75°, 오차 +0.02°)",
 "current_mm": {"x": -2.0, "y": 174.2, "z": 0.3},
 "homed": ["x","y","yaw","z"], "moving": false, "yaw_moving": false,
 "rejects": 0, "detail": "대기",
 "limit_mm": {"x": [-5.0, 408.7], "y": [50.9, 275.1]}}
```

| 필드 | 뜻 |
|---|---|
| `pose` | yaw 자세 1~4 (`0`=12시, `null`=모름/자세 사이) |
| `current_mm` | 현재 위치(mm). **호밍 전에는 `null`** 이다 |
| `homed` | 호밍된 축 목록 |
| `rejects` | 거부 누적. **늘어났으면 방금 거부된 것**이다 — `detail` 에 사유가 있다 |

### `/drive/status` (주행)

```json
{"moving": true, "goal_mm": -500.0, "moved_mm": -312.4, "left_mm": 187.6,
 "drift_mm": 0.4, "angles_ok": true, "rejects": 0, "detail": "..."}
```

`drift_mm` 은 좌우 바퀴 차이에서 온 **직진 이탈**이다. 30mm 를 넘으면 노드가 스스로 선다.

### `/safety/state` (`rebar_base_interfaces/msg/SafetyState`)

JSON 이 아니라 **메시지 타입**이다. 주요 필드: `estop`(bool), `stop_switch`,
`inputs_stale`, `blocked_axes`(문자열 배열).

## 3. UI 에서 보여줄 것 — 권장

**버튼 3개면 충분하다:** 전체 호밍 / 미션 시작 / 정지.

**반드시 보여야 하는 것:**

1. **호밍 여부** — `/stage/status` 의 `homed` 가 4개인가. 호밍 전에는 mm 이동이
   전부 거부되므로, 이게 안 보이면 "왜 안 움직이지" 로 헤매게 된다.
2. **비상정지** — `/safety/state` 의 `estop`. 걸려 있으면 **호밍도 미션도 거부된다.**
   실제로 "제어 권한을 못 받았다" 라는 엉뚱해 보이는 사유로 실패한다.
3. **실패 사유** — `state`/`phase` 가 `failed` 일 때 `detail` 을 그대로 띄울 것.
   사유 문장이 원인을 직접 말하도록 써 두었다.
4. **거부 누적** — `rejects` 가 늘면 `detail` 과 같이 띄울 것. 조용히 안 움직이는
   경우의 대부분이 거부다.
5. **통신 끊김** — 상태 토픽이 N 초 이상 안 오면 그것도 표시할 것. 로봇이 멈춘 것과
   UI 가 못 받는 것은 다른 문제인데 화면상으로는 똑같아 보인다.

**폴링 주기:** `/stage/status` 는 20Hz 로 나온다. UI 는 2~5Hz 면 충분하다.

## 4. 연결 방법

### (a) 노트북에 ROS 2 가 있으면 — 가장 단순

같은 네트워크에서 `ROS_DOMAIN_ID=33` 만 맞추면 토픽이 그대로 보인다. 중계가 필요 없다.

```bash
export ROS_DOMAIN_ID=33
ros2 topic echo /mission/status --field data
ros2 topic pub --once /mission/start std_msgs/Empty "{}"
```

### (b) 웹 UI — **이미 장비에 들어 있다** (권장)

브라우저만 있으면 된다. 노트북에 ROS 2 를 깔 필요도, UI 를 만들 필요도 없다.

```
http://192.168.0.16:8080      (동글 WiFi — 주 경로)
http://192.168.0.12:8080      (내장 WiFi — 예비)
```

`ui_bridge` 노드가 `teleop.launch.py` 에서 **자동으로 뜬다** (`use_ui:=false` 로 끈다,
포트는 `ui_port:=8080`). 화면은 브릿지가 같이 서비스한다.

**왜 DDS 직결이 아니라 HTTP 인가:** ROS 2 기본 탐색은 **멀티캐스트**다. 공유기·AP 를
거치면 막히거나 흘리지 않는 경우가 흔해 "같은 네트워크인데 토픽이 안 보인다" 가
된다 — 리허설 당일에 그걸 디버깅하게 된다. HTTP 는 유니캐스트라 라우터만
통과하면 된다. 노트북에 ROS 2 가 있으면 (a) 가 더 단순하니 그쪽을 써도 된다.

#### 엔드포인트

| | 하는 일 | 응답 |
|---|---|---|
| `GET /` | UI 페이지 (`ui_page.html`) | HTML |
| `GET /state` | 아래 5개 상태를 한 덩어리로 | JSON |
| `POST /cmd/homing` | `/homing_cmd "all"` | `{"ok":true}` |
| `POST /cmd/mission` | `/mission/start` | `{"ok":true}` |
| `POST /cmd/stop` | `/homing_cmd "stop"` + `/mission/abort` + `/stage/stop` | `{"ok":true}` |

알 수 없는 `/cmd/*` 는 `400 {"ok":false}` 다. **CORS 는 열려 있다**(`*`) — UI 를
노트북에서 띄우든 장비에서 받아가든 둘 다 된다.

```bash
curl -s http://192.168.0.16:8080/state | python3 -m json.tool
curl -X POST http://192.168.0.16:8080/cmd/stop
```

#### `GET /state` 응답

2장의 JSON 들을 그대로 담고, **얼마나 오래됐는지를 같이 준다.**

```json
{"homing": {…}, "mission": {…}, "stage": {…}, "drive": {…},
 "estop": false,
 "age_sec": {"stage": 0.1, "homing": 0.3, "drive": 0.2, "mission": 1.4, "safety": 0.1},
 "now": 1791366064.0}
```

- `age_sec` 는 **토픽별 마지막 수신 경과 초**다. ⚠ **값만 보면 안 된다** — 3초를
  넘으면 끊긴 것으로 띄울 것. 로봇이 멈춘 것과 UI 가 못 받는 것은 화면상
  똑같아 보이는데 원인이 전혀 다르다 (2장 3절 5번).
- 아직 한 번도 안 온 토픽은 `{}` 이고 `age_sec` 에 키가 **없다**.
- 깨진 JSON 은 버린다 — 옛 값이 남고 `age_sec` 만 늙는다. 쓰레기를 뿜는 노드가
  죽은 노드처럼 보이는 것이 맞는 해석이다.
- `estop` 은 `null` 일 수 있다 (`/safety/state` 를 아직 못 받음 = 모름).
  **`null` 을 `false` 로 취급하지 말 것.**

#### 직접 UI 를 만들 거면

`GET /state` 를 2~5Hz 로 폴링하고 `POST /cmd/*` 로 쏘면 끝이다. 기본 화면이
`src/rmd_robot_control/rmd_robot_control/ui_page.html` 에 **단일 파일**로 있으니
그걸 고치거나 베껴 쓰면 된다 (빌드 과정도 의존도 없다). `rosbridge_suite` 로
토픽을 그대로 노출하는 길도 있지만(`sudo apt install ros-humble-rosbridge-suite`),
명령·상태가 위 5개뿐이라 그만한 무게가 필요하지 않다.

⚠ 기본 화면은 **호밍·미션 버튼을 두 번 눌러야** 명령을 보낸다 (4초 내). 장비를
움직이는 명령이라 손이 스쳐서 나가면 안 된다. **정지는 한 번에** 나간다.

## 5. 리허설 흐름

```
전원 ON
   ↓  (약 1분 — 교차점 검출 모델 적재에 40초쯤 걸린다. 그 전에 미션을 걸면
   ↓   첫 검출이 버려져 "검출이 안 온다" 로 실패한다)
[전체 호밍]   /homing_cmd "all"        ← UI 의 [전체 호밍]
   ↓  refs 4개가 찰 때까지 — **실측 71초** (2026-10-07, z→x→yaw→y 완주)
[미션 시작]   /mission/start           ← UI 의 [결속 미션 시작]
   ↓  test_path.txt 경로: 시점 결속 → 후진 500mm 결속 → 전진 500mm 결속
완료
```

브라우저로 할 거면 `http://192.168.0.16:8080` 하나만 열면 된다 — 터미널 명령은
필요 없다. 호밍 전에는 UI 상단에 "호밍 전이다" 가 떠 있다.

⚠ **UI 정지를 1차 수단으로 삼지 말 것.** 가장 빠르고 확실한 정지는 **리모콘
비상정지**다. UI 는 와이파이→HTTP→ROS 를 거치므로 그만큼 느리고, 통신이 끊기면
눌러도 안 간다. 보조 수단이다.

**호밍 전에 yaw 를 12시로 맞출 필요는 없다.** 1번·4번 자세는 단회전만으로 못 가리는데,
X 를 먼저 호밍한 뒤 작업영역 카메라 영상으로 가린다. 못 가리면 **거부**되고 그때만
사람이 12시로 옮기면 된다.

**검증 기록 (2026-10-07).** 전원 재투입 후 UI 의 [전체 호밍] 하나로 4축이 완주했고
(71초), 자세는 1번으로 확정됐다 — 건 −16.71°, 목표 대비 **+0.06°**. X 호밍 뒤
영상으로 yaw 별칭을 가리는 경로도 이때 처음 실제로 동작했다
(`비전 판정: 후보 -13.91° / +14.89° 중 +14.89° 선택`). 노드 5개(카메라 검출·주행·
내비게이터·Pololu·ui_bridge) 자동기동도 같이 확인됐다.

## 6. 막혔을 때 — 당일 대응

위에서 아래로, **증상 → 먼저 볼 곳** 순이다. 당일에는 원인을 캐지 말고 되돌리는
쪽을 택한다.

### `sudo systemctl restart rebar-teleop` 이 "A dependency job … failed" 로 끝난다

**상부 전원부터 본다.** 서비스 설정 문제가 아니다.

Moxa USB 허브 체인이 상부체 전원을 받으므로, 상부를 내리면 그 아래가 통째로
사라진다 — PCAN-USB 2개(can2/can3), WiFi 동글(192.168.0.16), 카메라 3대, Pololu.
can2 장치가 없으면 `can2-up.service` 가 못 뜨고, teleop 은 그걸 `Requires` 한다.

    ip -br link | grep can      # can2·can3 가 있나
    lsusb | grep 0c72           # PEAK 가 보이나

전원을 올리면 USB 가 다시 열거되고 재시작이 그냥 된다 (2026-10-07 실측). 배선이나
드라이버를 뒤지지 말 것.

### 브라우저가 `192.168.0.16` 에 못 붙는다

동글이 빠졌거나 상부 전원이 내려가 있으면 **그 IP 자체가 없다.** 내장 WiFi 로
붙는다 — `http://192.168.0.12:8080`. UI 를 파일로 열어 쓰는 경우는
`?host=http://192.168.0.12:8080` 을 붙이면 된다.

    ip -br addr | grep 192.168.0

### 호밍이 yaw 에서 거부된다

"자세를 못 가린다" 로 끝나면 **사람이 yaw 를 12시로 옮기고 다시 [전체 호밍]** 을
누른다. 거부는 정상 동작이다 — 못 가린 채 돌리면 기구부로 밀기 때문이다.

### 호밍 중 yaw 가 스톨한다

**즉시 리모콘 비상정지.** 탐색 방향이 반대로 잡힌 증상이고, 2026-10-03 에 이걸로
커플링이 미끄러졌다. 복구 후 `axes.yaml` 의 `noon_single` 을 **눈대중 12시로 고치지
말 것** — 자세 1~4 가 전부 같이 밀려 Y 가 프레임을 친다. 근거는 호밍 로그의
`원점 확정 (… 단 NNNNNN)` 과 `edge_single_from_*` 의 대조다.

### 축 하나가 "에러" 로 멈췄는데 안 풀린다

Z 의 `0x4000` 은 `0x9B`(에러 클리어)로 **안 지워진다.** Z 축 전원 재투입만 듣는다.
2차년도 비트표에 'Reserved' 로 적혀 있어 의미는 아직 모른다.

### 갑자기 전 축이 응답하지 않는다

can2 가 bus-off 에 갇히면 `<NO-CARRIER> state DOWN` 이 되고 **카운터가 동결된다** —
이때 "에러 +0" 은 깨끗한 게 아니라 컨트롤러 정지다. 되살리는 법:

    ip -br link show can2                    # DOWN 이면 bus-off
    sudo systemctl restart can2-up           # 되살린다
    ~/peak-driver/can2_health.sh 5           # 연결 대수·오염 판정

⚠ **상부체 CAN 가지를 의심하지 말 것 — 2026-09-15 의 오진이다.** 진짜 원인은
250 kbps 리모콘 수신기가 1 Mbps 모터 버스에 단자대에서 묶여 있던 것이었고
(2026-09-18 규명), PCAN-USB 를 하나 더 써서 `can3` 로 분리해 2026-09-29 에
끝났다. **접지·종단도 배제 확정이다** — GND 전위차 171 mV(허용범위의 2%),
종단 `CAN_H↔CAN_L = 60Ω` 2개가 정상값. 다시 뜯지 말 것.

⚠ 에러는 **개수가 아니라 종류로 본다.** 모터를 폴링하면 무해한
`error-on-tx @ acknowledge-slot` 이 초당 수천 개 나온다(없는 노드에 보내서 ACK 를
못 받는 것). 실제 오염은 `tolerate-dominant-bits` 같은 **수신 측 위반**이고
berr-counter 의 **rx** 가 오른다.

### 횡이동

`path_generation/test_path.txt` 는 **이미 전후진 왕복만** 들어 있다(y 전부 0). 기구가
안 고쳐졌으면 그대로 쓰면 되고, 따로 끌 것이 없다. 고쳐졌으면 사각형 경로는
`test_path_rect.txt` 에 있다.

### 서비스를 재시작했다 / 전원을 재투입했다

**무조건 [전체 호밍] 부터.** 멀티턴은 전원에 날아가므로 축별 위치를 모르는 상태다.
축을 골라 호밍하지 말 것 — 축마다 간섭 구간이 달라서 건너뛰면 프레임끼리 부딪힌다.

### 그 밖에 챙길 것

- **배터리.** 한 번 떨어져서 장비가 꺼진 적이 있다.
- **전원 ON 후 1분은 기다린다.** 교차점 검출 모델 적재에 40초쯤 걸리고, 그 전에
  미션을 걸면 첫 검출이 버려져 "검출이 안 온다" 로 실패한다.
- **상부축에는 전류 보호가 없다.** 속도·가감속을 올려둔 상태이므로, 이상음이 나면
  전류를 기다리지 말고 사람이 멈춘다.
