## 1. 주행모터 — 가감속은 "모터축" 기준이었다 ★핵심 발견

### 배경
0x141·0x142를 둘 다 RMD X4-10 → **X4-36**으로 교체한 뒤, 파라미터가 좌우 다를 것으로
의심해 점검했다. 결과: **이미 완전히 동일**했다(가감속 1200/1200, 토크 69/69,
최고속 498/498, 위치계획 5000/5000, 펌웨어 2026042402, PID 6개 값 전부 일치).
즉 "142를 141과 맞추는" 작업은 할 게 없었다.

### 진짜 문제
실제 증상은 **가속이 굼뜨고 정지에 한참 걸리는 것**이었고, 원인은 단위 해석이었다.

리모콘 수동주행에서 지령을 3초간 고정했을 때 실측 가속도가 **35.7 출력축 dps/s**.

| 후보 | 예상값 | 실측 35.7과 |
|---|---|---|
| 0x43이 출력축 기준 | 1200 dps/s | 34배 차이 ❌ |
| 슬루 `accel_limit_mps2` 0.25가 제한 | 500 dps/s | 14배 차이 ❌ |
| **0x43이 모터축 기준** | 1200÷36 = **33.3** | **+7% 일치** ✅ |

> **방증**: 혼합 구성 시절 현장에서 실측으로 맞춘 비대칭이 1200(X4-36)/500(X4-10) = 2.4배.
> 기어비 비율 36/12.5 = 2.88배. **그 보정의 정체가 기어비였다.**

⟹ 감속비 12.5 → 36 교체로 **같은 설정값의 실효 램프가 1/2.9**이 됐다.

| | 0x43=1200 | 출력축 | 0→최고속 |
|---|---|---|---|
| X4-10 시절 | 1200 | 96 dps/s | 5.2초 |
| X4-36 (교체 직후) | 1200 | **33 dps/s** | **14.9초** |

**⚠ 모터 모델을 바꾸면 0x43 값도 감속비만큼 다시 곱해야 한다.** 좌우만 맞춰선 안 된다.

### 조치 (`scripts/service/robot_control_service.sh`)
가속과 감속을 **분리**했다. 전엔 `--set 1200` 한 번으로 index 2·3을 같이 썼는데 둘은
성격이 정반대다.

```bash
DRIVE_ACCEL=3456    # = 96 출력축 dps/s × 36. X4-10 시절 검증된 출력축 램프 복원
DRIVE_DECEL=12000   # = 333 출력축 dps/s. 감속은 회생이라 전류 피크 제약 없음
```

- **가속은 이 이상 올리지 말 것** — 그 램프가 전류 피크 28.3A·시스템 프리즈와 겹쳤던
  지점이다(2026-08-14).
- **X4-36은 0x43이 ROM에 안 남는다** → 서비스가 매 기동 재적용한다. 값을 바꾸려면
  이 스크립트와 `tools/motor/check_drive_pair.py`의 `TARGET_ACCEL`/`TARGET_DECEL`을
  **같이** 고칠 것.
- `can_devices.yaml`에 슬루 파라미터를 명시했다(전엔 코드 기본값만 있어 안 보였다):
  `accel_limit_mps2: 0.25`(올리지 말 것) / `decel_limit_mps2: 0.8 → 2.5`.

### 결과 (실측, 7구간 총 5m)
- 가속 35.7 → **94 출력축 dps/s** (예측 96, 오차 2%). 주행·선회 안정적.
- 정지거리는 **속도의 제곱**에 비례:

| 직전 속도 | 정지거리 | 시간 |
|---|---|---|
| 142 dps | 12 mm | 0.40 s |
| 192 dps | 24 mm | 0.55 s |
| 264 dps | 44 mm | 0.75 s |
| 307 dps | 66 mm | 0.90 s |

  역산 실효 감속도 ≈ 380 출력축 dps/s (설정 333 + 슬루 몫).
- **자율주행은 이미 충분하다**: `rebar_drive`가 목표 80mm 전부터 `approach_scale 0.5`로
  0.05 m/s(100 dps)까지 줄이므로 정지거리 **≈7 mm** < 도달오차 15 mm.
  더 올릴 실익이 적다(30000으로 올려도 7 → 3 mm).

### 직진성 — 손댈 게 없다
7구간 좌우 이동거리 차: `-0.09% / -0.00% / -0.01% / +0.04% / -0.00% / +0.01% / +0.01%`
→ **사실상 0.** 트림(`left/right_speed_trim`)은 1.0 유지. 전류 최대 2.3A, 온도 29~31°C.

### ⚠ 사용자 체감 정정
"토크가 높아져서 안정적"이라고 느끼셨지만 **토크는 안 바뀌었다**(69% 그대로, 전류도
상한의 절반 이하). 달라진 건 램프다 — 토크는 원래 있었는데 쓰이질 못하고 있었다.
**철근을 타넘다 못 넘으면 그건 여전히 69% 상한 문제**고, 그때는 좌우 같이 100%
(=10.5 N·m, X4-36 연속정격)로 올리면 된다.

## 2. 도구 버그 2건 — 둘 다 잘못된 결론을 낳았다

### ① `rmd_pid.py` — 0x30은 `index + float32` 형식이다
"0x30이 전부 0으로 읽힌다 → 이 펌웨어는 미지원"이라고 2026-09-09에 조사를 접었는데
**도구가 형식을 틀리게 읽고 있었다.** 버스 점유 탓도 아니다(같은 순간 같은 필터로
0x42는 1200을 정확히 읽었다).

```
요청  [0x30, index, 0, 0, 0, 0, 0, 0]
응답  [0x30, index, 0, 0, float32(LE)]      ← DATA[4:8]   (0x42와 같은 꼴)
```

실측 (0x141·0x142 **완전히 동일**):
```
index 0 = 0      index 1 = 1.5    index 2 = 0.05
index 3 = 0      index 4 = 0.01   index 5 = 0.0001
```
⟹ PID는 좌우 동일 = 직진 틀어짐의 원인이 아니다.

**⚠ 쓰기는 막아뒀다.** 어느 index가 speedKp/Ki인지 데이터시트 미확인. 옛 바이트 6개
형식으로 쓰면 index 0에 엉뚱한 float가 들어가 **구동 중 루프 게인이 날아간다.**

### ② `MotorFeedback.current_current`는 **mA**다
`can_parser`가 `int(torque_current * 1000)`으로 넣는다(`drive_controller`도 /1000).
새로 만든 도구에서 /100으로 읽어 **10배 뻥튀기**된 전류(15~23A)를 보고 "부하 이상"으로
오판할 뻔했다. 교차검증 셋이 전부 반박했다:
서비스 로그 "전류 제한"(6A) 발동 **0회** · 온도 28°C 고정 · X4-36 실측(평균 0.3A/최대 3.0A).

> **교훈: 수치가 이상하면 독립 경로와 대조할 것.**

## 4. seg 모델 — 9클래스 교체 + **인덱스 역전 사고 예방** ★중요

`rebar_seg_260914.pt` (Lightning + smp DeepLabV3Plus/mobilenet_v2, head `(9,256,1,1)`).
`src/rebar_vision/model/`로 복사해 기본 가중치로 지정.

```
기존 7: background floor human obstacle rebar_h rebar_v wall
신규 9: background floor human level_rod obstacle plate rebar_h rebar_v wall
                              ↑신규            ↑신규
```

| idx | 기존 | 신규 |
|---|---|---|
| 3 | obstacle | **level_rod** |
| 4 | **rebar_h** | **obstacle** |
| 5 | **rebar_v** | **plate** |
| 6 | wall | **rebar_h** |

### 위험했던 것
`deck_edge.py`가 `REBAR = [4, 5]`처럼 **인덱스를 하드코딩**하고 있었다. 가중치만 바꾸면
**"주행가능 = obstacle + plate"**, **"주행불가 = 진짜 철근"** 이 된다 — 판정이 통째로
뒤집혀 데크 밖으로 나간다. 지금은 head 크기 불일치로 로드가 실패해 시끄럽게 죽지만,
누군가 `CLASS_MAP`만 늘리고 `deck_edge`를 안 고치면 **조용히** 뒤집힌다.

### 조치 — 인덱스를 **이름에서 유도**
- `rebar_seg.CLASS_MAPS = {7: {...}, 9: {...}}`. `RebarSegmenter`가 체크포인트의 최종
  conv `out_channels`로 **자동 선택**하고 `self.class_map`을 노출.
  **등록 안 된 클래스 수는 로드 거부** — 추측해서 돌리느니 안 도는 게 낫다.
- `deck_edge.set_class_map()` / `rebar_grid.set_class_map()`이 이름으로 재계산.
  **`deck_edge_node`가 seg 로드 직후 호출한다 — 이 호출이 빠지면 판정이 뒤집힌다.**
- **`NONDECK = REBAR의 여집합`**으로 정의 → 클래스가 또 늘어도 "모르는 것 = 주행불가"
  (안전한 쪽)로 자동 수렴.
- 팔레트도 이름 기준(`PALETTE_BY_NAME`), `colorize(mask, class_map)`.
- ✅ 구 7클래스 모델로 되돌려도 결과 동일함을 검증(`REBAR=[4,5]`, `OBSTACLE=[2,3]`).

**기동 시 이 줄을 반드시 확인할 것:**
```
seg 클래스 9개 → 주행가능=['rebar_h', 'rebar_v'] · 즉시정지=['human', 'obstacle'] · level_rod=3 · plate=5
```
주행가능이 `rebar_h/rebar_v`가 아니면 **즉시 중단**. 판정이 뒤집힌 상태다.

### 새 클래스 처리 방침
- **`plate`** (데크 가장자리 H빔 형상 철판) = **주행불가**. NONDECK 여집합에 자동 포함.
  **즉시정지(hard_stop)는 아니다** — 모델 정확도가 아직 낮아 오검출 시 급정지가
  잦아지는 것을 피했다.
- **`level_rod`** = 기존 **색 기반과 OR**. `de.level_rod_seg(mask)`가 색 기반과 **같은
  지표**(가장 가까운 봉 밑동 y/H)를 내고 `max()`로 합친다.
  - 색 기반은 **좌측 카메라에서 못 쓴다**(녹슨 철근이 봉보다 노랗다)
  - seg는 데이터가 적어 정확도가 낮다
  - → 한쪽만 믿지 않는다. 어느 쪽이든 잡으면 멈춘다.

| `heading_offset_front_deg` | **−1.13** | **0.0** ← 실측 영점이 사라짐 |
| `heading_offset_back_deg` | **+1.52** | **0.0** ← |
| `heading_rev_gain` | 0.53 | 0.53 ✅ |

실측 영점이 0으로 덮여 **지속적으로 한쪽으로 치우친 조향**이 나간다. 게인은 5배 높고
데드밴드는 1/3이라 훨씬 공격적으로 튼다.

**게다가 오늘 seg 모델을 7→9클래스로 바꿨다.** 메모리에 *"추정기·해상도를 바꾸면 영점
재캘리브 필수"* 라고 기록돼 있는데 모델 교체도 같은 범주다. **−1.13/+1.52 자체도 지금은
못 믿는다.**

→ 자율작업을 돌리면 헤딩제어는 "동작은 하지만 영점이 안 맞는" 상태다.
**직진성을 보려면 `heading_enabled:=false`로 끄고 먼저 돌려볼 것.**

## 6-2. 횡이동 모터 부하 재측정 ✅ (신품 교체 후)

기존 측정은 전부 **고장 직전 모터** 기준이라 전제가 틀려 있었다. 신품으로 같은 기구·
같은 동작을 실측(`tools/diag/lateral_probe.py`, 실제 부하 걸린 횡이동 3회):

| 항목 | 옛 모터(고장직전) | 신품 | |
|---|---|---|---|
| 최대 전류(rms) | 21.7 A | **14.7 A** | −32% |
| → 드라이버 상한 21.5A 대비 | **101%**(잘림) | **68%** | 여유 0% → **32%** |
| 평균 전류(rms) | 4.5 A | **2.7 A** | −40% |
| → 연속정격 6.1A 대비 | 73% | **44%** | |
| 한계부근(90%↑) 체류 | 있음 | **0.00초** | ★ |
| 온도 | — | 33→42°C (25.6초 연속이동 포함) | |

⟹ **30A는 기구 용량 부족이 아니라 모터 개체의 열화였다.**
   "승강 스트로크 50~60mm 축소" 검토는 **불필요**하다.

- 토크 상한으로 보호막은 여전히 불가 — 피크가 정격의 **241%**인데 파라미터가
  uint8(최대 255%)이라 정상 동작을 안 막으면서 스톨만 거르는 여유가 없다.
  `lateral_max_torque_pct: 0`(무제한)이 맞다. **실질적 보호막은 온도.**
- ⚠ **순간 샘플로 판단하지 말 것** — 한 번의 이동 안에서 전류가 5.5배 출렁인다
  (평균 3.8A ↔ 최대 20.8A, 진폭). 순간값 6개를 보고 "무부하"라고 오판했다.
  0x9C 의 `iq` 는 **진폭**이므로 데이터시트(rms) 비교 시 √2로 나눌 것.
- `tools/diag/lateral_probe.py` 강화: 온도 추적 · rms 환산 · 한계부근 체류시간 ·
  70/85°C 경고 · 종료 시 요약.

**미검증**: 연속으로 여러 레인을 넘길 때의 **누적 발열**. 옛 모터를 죽인 건 단발
피크가 아니라 누적이었다. 자율작업 중 같이 띄울 것:
```bash
python3 tools/diag/lateral_probe.py --sec 3600   # → /var/log/robot_control/lateral_probe.csv
```

```bash
python3 tools/vision_test/gmsl4_watch.py --min 10      # compressed 구독(운용 조건)
```

`plate` / `level_rod` 검출이 실제로 맞는지도 눈으로 볼 것.

### 우선순위 D — 자율작업 횡이동 실동작
`rebar_drive_lateral:=true`로 켜뒀다. 좌·우 카메라가 둘 다 살아있으므로 양쪽 판정이
나온다. 측면 판정 타임아웃은 45초.
⚠ 횡이동 모터(0x143)는 오늘 신품 교체 + `home_angle_94` 19.26으로 재캘리브된 상태.

### 그 밖에 (낮은 우선순위)
- **직진 트림**: 엔코더상 좌우 0.0x%라 보정 불필요. 줄자 실측으로 최종 확인만:
  `python3 tools/motor/straight_drive_test.py --drift <횡편차_m> --dist 3.0`
- **오도메트리 거리 스케일**: `dps_to_mps_scale 0.989`가 speed 모드 전용이라 현재
  position 모드엔 미적용. 3m에 ~33mm 오차 가능 → 결속 피치에 영향.
- **`speed_scale_factor` 포화**: 0.25 m/s × = 500 dps인데 모터 한계 498 dps.
  풀스틱이면 포화에 닿아 트림이 잘린다. 0.24 정도로 내리면 여유가 생긴다.
- **pololu 트리거 USB 없음**: `/dev/pololu_trigger` 미존재로 `pololu_node` 오류.
  결속 트리거라 자율결속 전에 확인 필요.
- `rmd_pid.py` 쓰기 재개하려면 데이터시트의 0x30 index 표 확인 필요.
